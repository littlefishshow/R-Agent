# Paper Repo Code Research

## When to Use
- 用户已有论文阅读笔记，并要求阅读/调研论文配套开源仓库。
- 用户想知道：论文核心方法在代码里对应哪些文件、类、函数、配置，而不是想看完整代码百科。
- 用户希望把源码调研结果追加到原论文总结 Markdown 后面。

## Goal
最终输出必须帮助用户回答一个问题：

> **论文中的核心方法，在源码里到底是怎么落地的？**

优先产出“可定位、可追踪、可改造”的代码阅读结果，而不是冗长仓库说明。

## Default File Policy
- 论文总结默认在 `outputs/papers_output/` 中定位；结果追加到原 Markdown 末尾。
- 仓库默认克隆到 `sandbox/paper_repos/<repo_name>/`。
- 临时目录树、grep 结果、草稿放到 `sandbox/paper_repo_research/<repo_or_paper>/`。
- 不主动下载大模型、大数据集、权重或启动长训练；需要运行时优先做静态调研或极小 dry-run。

## Required Workflow

### 1. 先从论文笔记提取“要找什么”
读取原论文总结，只提取以下信息：

- 论文一句话方法。
- 3-6 个核心术语/模块/贡献。
- 训练目标、loss、奖励、数据构造、推理策略等关键机制。
- 用户特别关心的问题。

不要把论文笔记重新总结一遍；它只用于生成源码阅读的搜索清单。

### 2. 确认仓库与版本
必须确认并记录：

- repo URL。
- 官方/第三方性质。
- branch 与 commit SHA。
- 本地路径。

若仓库已存在，先检查 remote 与当前 commit；不要无脑覆盖。

### 3. 第一轮只建立“源码导航图”
快速检查 README、configs、scripts、docs、setup/pyproject、顶层目录。目标不是详述每个目录，而是定位：

| 问题 | 必须回答 |
|---|---|
| 怎么跑 | 推荐 train/eval/demo 命令在哪里 |
| 配置在哪 | 哪些 config 控制论文实验/核心方法 |
| 入口在哪 | train/eval/infer 主入口 |
| 核心实现在哪 | 最可能承载论文创新的文件/类/函数 |
| 不读哪里 | 明确跳过 logger、distributed、misc 等低信息工程细节 |

### 4. 第二轮追“最小执行链”
只追一条最小闭环，格式固定为：

```text
入口脚本
  -> 配置加载
  -> 数据/环境/样本构造
  -> 模型或策略调用
  -> 核心方法模块
  -> loss/reward/update 或 inference/eval
  -> 输出指标/结果
```

阅读源码时优先找这些函数：

- 数据：`__getitem__`、`collate_fn`、`preprocess`、`tokenize`、`build_batch`、`get_lm_inputs`。
- 模型：`forward`、`generate`、`predict`、`encode`、`decode`、`build_model`。
- 训练：`training_step`、`compute_loss`、`compute_reward`、`compute_advantage`、`train_one_epoch`、`update_*`。
- 评测：`evaluate`、`metric`、`score`、`postprocess`。

如果项目是 RL/agent/online environment，不强行套 `Dataset.__getitem__`；应改为追“环境状态 → prompt/action → reward/history → update batch”。

### 5. 第三轮只深读“论文核心方法对应代码”
必须建立下面这张表，并把它作为最终输出的核心：

| 论文核心点 | 代码对象 | 文件路径 | 何时调用 | 输入/输出 | 关键实现细节 | 如何关闭/替换 |
|---|---|---|---|---|---|---|

要求：
- 每个论文核心点至少对应一个具体代码对象：类、函数、配置项或脚本。
- 说明它在训练时还是推理时生效。
- 说明输入输出的数据结构；能给 shape 就给 shape，不能给就给字段名/字典结构。
- 说明与 baseline 相比多了什么。
- 找到 ablation/config 开关；如果没有，明确说“未找到显式开关”。

### 6. 只保留高信息工程细节
源码框架细节只写会影响理解、复现或改造的内容，例如：

- 配置默认值与论文实验配置不一致。
- 数据/权重/索引/外部服务未开源或下载量大。
- 训练与推理链路不一致。
- 关键模块只在某个 config 开启。
- reward/loss/metric 的实现与论文表述存在差异。
- 有硬编码路径、固定模型名、特殊 token、环境假设、batch/group 约束。
- 依赖 GPU、Ray、vLLM、CUDA、外部 API 或特定服务。

不要展开：普通 logger、wandb 表格样式、checkpoint 保存细节、分布式样板代码、无关 helper 函数，除非它们直接影响核心方法。

### 7. 可选运行验证
静态阅读优先。只有在低成本且不会触发大下载/长训练时才运行：

- `--help`。
- 打印合并后的 config。
- 跑 tiny test。
- 构造 1 条 fake batch 看关键函数输入输出。

如果会下载模型/数据、占用 GPU、启动 Ray 集群、调用外部 API，先说明风险，不要直接运行。

## Output Requirements
最终必须追加到原论文总结 Markdown。默认使用下面的精简结构，避免冗长：

```markdown
---

## 开源仓库源码阅读（YYYY-MM-DD）

### 1. 本次源码阅读结论
- 一句话结论：论文核心方法主要落在 `...`。
- 我认为最关键的 3-5 个文件：
  1. `path`: 为什么关键
  2. `path`: 为什么关键
- 本次没有深读/不值得深读的部分：...

### 2. 论文核心方法 ↔ 代码定位表
| 论文核心点 | 代码对象 | 文件路径 | 何时调用 | 输入/输出 | 关键实现细节 | 如何关闭/替换 |
|---|---|---|---|---|---|---|

### 3. 最小执行链
```text
入口 -> ... -> 输出
```

用 1-3 段说明这条链路，不展开无关工程细节。

### 4. 关键源码解读
按“核心方法”分小节，每节只写：
- 代码位置。
- 它做了什么。
- 它为什么对应论文方法。
- 需要注意的实现细节/坑。

### 5. 配置、复现与改造注意事项
- 关键配置：...
- 默认配置 vs 论文配置：...
- 数据/权重/环境依赖：...
- 最小 sanity check：...
- 如果要改造，优先改哪里：...

### 6. 仍不确定/需要进一步验证
- ...

### 源码阅读重检查记录
- commit/branch：...
- 对照范围：论文笔记 / README / configs / scripts / 入口 / 核心方法文件
- 已验证：章节已追加、代码围栏闭合、关键表格完整
```

## Quality Checklist
完成前检查：

- 是否先从论文总结提取核心方法，而不是直接泛读仓库？
- 是否给出最关键 3-5 个文件，而不是目录百科？
- 是否有“论文核心方法 ↔ 代码对象”表？
- 是否追出最小执行链？
- 是否说明核心方法训练/推理何时调用？
- 是否说明输入输出数据结构？
- 是否说明如何关闭/替换论文创新模块？
- 是否只保留影响复现/理解/改造的工程细节？
- 是否明确哪些部分没深读、为什么不读？
- 是否把结果追加写入原论文总结？
- 是否验证 Markdown 代码围栏闭合？

## Common Pitfalls
- 输出变成仓库 README 摘要，没有定位核心代码。
- 表格很多但没有解释“为什么这段代码对应论文方法”。
- 写了大量目录、依赖、logger、wandb、分布式细节，稀释核心信息。
- 不区分默认配置和论文实验配置。
- 不说明训练时/推理时是否都启用。
- 不说明如何关闭或替换创新模块。
- 没有把最终结果写回原论文总结。
