# Codebase Scout

## When to Use

当用户给一个代码仓库，并且仓库比较大或项目比较复杂，需要你先理解它，再做修复、开发、重构、审计、写文档或构建 autoresearch 项目时，使用本 skill。

小而简单的项目不一定需要触发本 skill，父进程可以直接读关键文件。这个 skill 主要解决“大或复杂导致父进程不能靠一次串行阅读稳定理解”的情况。

典型请求：

- “帮我读一下这个仓库”
- “先理解项目结构再改”
- “这个 bug 应该从哪里看起”
- “我要加一个功能，先看看相关模块”
- “构建 autoresearch 项目前先读懂这个仓库”
- “大仓库不要一个 LLM 串行全读，能不能分批阅读”
- “这个项目文件不算特别多，但入口、配置、测试和运行链路很复杂，先帮我拆开读”

## Core Idea

读仓库不是逐文件通读。正确做法是：

```text
先问目标 -> 看地图 -> 找入口 -> 找验证命令 -> 沿关键路径读 -> 必要时分派子 Agent -> 汇总成可追溯报告
```

为什么要这样：

- 目标不同，应该读的文件不同。
- 仓库大时，一个 LLM 串行全读会浪费上下文。
- 先找入口和验证命令，后面改代码才知道怎么跑。
- 子 Agent 只读一小块，父进程只收摘要和文件引用，可以减少上下文膨胀。

## Modes

根据用户目标选择阅读模式：

| mode | 什么时候用 | 重点 |
|---|---|---|
| `overview` | 想整体理解仓库 | 架构、目录、入口、模块关系 |
| `bugfix` | 要修 bug | 报错栈、失败测试、相关调用链 |
| `feature` | 要加功能 | 相似功能、扩展点、接口和测试 |
| `refactor` | 要重构 | 边界、依赖、风险、回归测试 |
| `security` | 做安全审计 | 输入边界、权限、网络、文件、命令执行 |
| `tests` | 梳理测试体系 | 测试命令、fixture、CI、覆盖缺口 |
| `autoresearch` | 给 R-Agent 构建 autoresearch 项目脚手架前使用 | 研究目标、可改范围、评估入口、训练入口、smoke/full/long_job 命令、产物和风险 |

如果用户没有指定 mode，默认先用 `overview`，然后根据任务切到更具体的模式。

## Parent Workflow

### 1. 先确认目标

先用一句话写下本次阅读目的：

```text
阅读目标：为了 <bugfix/feature/refactor/autoresearch/...>，需要理解 <模块/运行链路/验证方式/...>。
```

不要一上来全仓库乱读。

### 2. 快速看仓库地图

优先用这些命令/文件建立地图：

```text
rg --files
README*
docs/
pyproject.toml / package.json / go.mod / Cargo.toml / pom.xml
Makefile / Dockerfile / docker-compose*
scripts/
tests/
```

要记录：

- 语言和框架；
- 启动入口；
- 测试入口；
- 构建/部署入口；
- 主要目录职责；
- 哪些目录不要优先读，例如 build、dist、node_modules、venv、outputs。

### 3. 找“程序怎么跑起来”

必须找这些入口，能找到多少算多少：

- CLI 入口；
- Web server 入口；
- worker/job 入口；
- route 注册；
- plugin/skill 注册；
- config 加载；
- main loop；
- train/eval 脚本；
- test 命令。

如果读仓库是为了构建 autoresearch 项目，必须特别找：

- 可修改文件范围；
- 评估入口；
- 训练/实验入口；
- metrics 输出位置；
- 最便宜的 smoke test；
- 昂贵的 full run 或 long job。

### 4. 判断仓库大小，决定是否分派子 Agent

小仓库父进程可以直接读。

大仓库或复杂项目建议分派子 Agent。判断条件：

- 文件很多，目录很多；
- 多语言或多服务；
- 入口不明显，例如 CLI、server、worker、插件、训练脚本分散在不同目录；
- 配置链路复杂，例如 YAML/JSON/env/命令行参数多层组合；
- 测试和验证链路复杂，例如 unit、smoke、integration、full eval、long job 分多层；
- 运行有远程服务、队列、GPU、数据库、外部 API 或平台依赖；
- 单个模块超过父进程上下文预算；
- 单个文件代码量非常大，但父进程仍需要知道它大致干什么、有哪些关键类/函数/入口；
- 需要同时理解测试、入口、业务、工具、配置；
- 用户明确要求并行调研。

分派原则：

- 子 Agent 只读，不改文件。
- 每个子 Agent 只负责一个清晰范围。
- 父进程不要把完整子上下文塞回主对话，只收摘要、关键文件和结论。
- 子 Agent 输出必须引用文件路径、函数/类名、命令。

### 5. 子 Agent 分派模板

#### 按大文件分派

当某个文件很长，父进程不适合整文件读入上下文，但又需要理解它的大致职责和关键代码时，可以把该文件交给一个只读子 Agent。

使用场景：

- 文件很大，直接读会占用太多上下文；
- 该文件是入口、核心 loop、模型、路由、训练脚本、工具注册、配置加载等关键文件；
- 父进程只需要知道“这个文件大致干什么、关键函数/类在哪里、后续应该重点读哪里”；
- 需要多个大文件并行概览。

当需要同时阅读多个大文件时，可以并发启动多个只读子 Agent，每个子 Agent 只负责一个文件或一组强相关文件。这样父进程不用串行读完所有长文件，也不会把所有源码塞进主上下文。

并发规则：

- 只读任务可以并发；
- 每个子 Agent 的文件范围必须清楚，例如“只读 `core/agent.py`”；
- 不要让多个子 Agent 对同一个文件给出互相覆盖的修改建议；
- 子 Agent 不写文件，所以并发不会产生写冲突；
- 父进程最后统一合并摘要，并抽查关键结论。

推荐子任务：

```text
你是只读代码阅读子 Agent。请只阅读文件 <path>，不要修改任何文件。

目标：
1. 用 5-10 条说明这个文件整体负责什么；
2. 列出关键类、函数、入口、全局变量或配置；
3. 说明主要控制流：从哪里进入、调用哪些重要函数、输出什么；
4. 标出和本次目标最相关的代码片段，引用函数/类名和可定位文本；
5. 标出风险点、复杂点、隐藏副作用；
6. 如果文件太长，不要逐行复述，只总结结构和关键位置；
7. 输出“建议父进程接下来精读的行/函数/类/搜索关键词”。

输出格式：
- 文件职责
- 关键结构
- 关键控制流
- 与任务相关的代码点
- 风险/疑问
- 建议父进程继续查看的位置
```

多个文件并发时，推荐任务列表形态：

```text
子任务 A：只读 core/agent.py，总结 Agent 主循环、消息流、工具调用入口。
子任务 B：只读 tools/delegate_tool.py，总结子进程调度、上下文 artifact、失败处理。
子任务 C：只读 core/prompt_builder.py，总结 system prompt、skill/memory/todo 注入方式。
```

父进程收到结果后，必须合并为一张表：

| 文件 | 职责 | 关键入口 | 和本次任务的关系 | 风险 | 还要精读哪里 |
|---|---|---|---|---|---|

限制：

- 子 Agent 只能读，不能写；
- 不要把整个文件复制回父进程；
- 不要输出大段源码，只输出短片段或可搜索关键词；
- 如果结论来自猜测，必须标成“猜测”，不能当事实。

#### 按目录分派

可以按目录分：

```text
你是只读代码调研子 Agent。请阅读 <目录/模块>，不要修改文件。

目标：
1. 说明这个模块负责什么；
2. 找入口函数/类；
3. 找它依赖谁、被谁调用；
4. 找测试文件和运行方式；
5. 找风险、 TODO、复杂点；
6. 输出关键文件路径和行号线索；
7. 给父进程一个 10 条以内摘要。
```

也可以按问题分：

```text
你是只读代码调研子 Agent。请围绕问题 <bug/feature/refactor/autoresearch目标> 阅读相关文件，不要修改文件。

输出：
1. 相关入口；
2. 调用链；
3. 需要修改或谨慎保护的文件；
4. 最小验证命令；
5. 还缺哪些信息。
```

### 6. 父进程汇总

父进程收到子 Agent 报告后，要做两件事：

1. 抽查关键结论，避免子 Agent 猜错。
2. 合并成一份结构化报告。

## Required Output

每次 codebase scout 最终输出应包含：

```text
1. 阅读目标
2. 仓库概览
3. 技术栈
4. 启动/构建/测试/验证命令
5. 目录结构说明
6. 核心入口
7. 关键模块关系
8. 数据流或控制流
9. 可修改范围和禁止修改范围
10. 已发现的问题/风险
11. 下一步建议
12. 还需要继续阅读的文件
13. 证据索引：文件路径、函数/类名、命令、artifact 路径
```

## Output for Building an AutoResearch Project

如果这个 skill 是给 R-Agent 构建 autoresearch 项目脚手架使用，输出还必须额外包含：

```json
{
  "research_goal": "本次研究目标",
  "editable_areas": ["可以改的目录或文件"],
  "protected_areas": ["不能改或要谨慎的文件"],
  "entrypoints": {
    "train": ["训练/实验入口命令"],
    "eval": ["评估入口命令"],
    "smoke": ["便宜验证命令"],
    "full": ["完整验证命令"],
    "long_job": ["长任务提交/监控命令"]
  },
  "artifacts": {
    "metrics": ["指标文件"],
    "logs": ["日志文件"],
    "outputs": ["输出产物"]
  },
  "module_map": [
    {"path": "目录或文件", "role": "职责", "risk": "风险"}
  ],
  "open_questions": ["还不确定的问题"],
  "recommended_project_scaffold": ["建议创建或更新的 autoresearch 项目文件"]
}
```

## What Not to Do

- 不要一开始逐文件通读。
- 不要把大日志、大文件、大量源码直接塞进父进程上下文。
- 不要把猜测写成事实。
- 不要让子 Agent 改代码。
- 不要在不知道成本时运行长训练或远程任务。
- 不要把测试命令和最终评估命令混为一谈。

## Why This Skill Exists

没有这个 skill 时，Agent 容易：

- 看错入口；
- 忽略测试命令；
- 读太多无关文件；
- 在大仓库里上下文爆炸；
- 改代码前不知道怎么验证；
- 给构建 autoresearch 项目的 R-Agent 一个空泛脚手架。

有这个 skill 后，R-Agent 可以先拿到“项目地图”，再生成 `program.md`、`eval.sh`、`train/train.sh` 和报告，而不是拍脑袋搭脚手架。未来如果 autoresearch loop 的 Planner 需要阅读大型仓库，也可以复用同一份 codebase scout 报告，但这不是本 skill 的唯一目的。
