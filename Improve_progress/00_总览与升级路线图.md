## 怎么读这个文件夹

- 每份 `NN_xxx.md` 对应 deer-flow 学习文档里的一个（或几个）章节。
- 文档开头都有一个**状态**字段，方便你我随时知道进度：
  - `📋 计划中` —— 还没动手，只有简略计划。

  1. **要解决什么问题**（R-Agent 现状 + 痛点）

## R-Agent 现状速览（升级前基线）

这是在真实代码里核对过的现状，不是泛泛而谈。关键文件：

| 关注点 | 现在在哪 | 现状一句话 |
| --- | --- | --- |
| 主循环 | `core/agent.py:891` `RAgent._loop` | 一个大 `while` 循环，所有逻辑挤在一起 |
| 状态 | `core/agent.py:348` `self.messages` 等散落属性 | 没有统一 ThreadState，靠 `messages` + 磁盘文件拼 |
| 上下文压缩 | `core/context_control.py`、`core/context/tool_result_storage.py` | 已有三层（对话压缩/大结果落盘/turn 预算），但摘要是字符串拼接非 LLM 摘要 |
| 上下文注入 | `core/prompt_builder.py:231`、`main.py:1421` | memory 被拼进 system prompt；**没有当前日期注入**，memory 权限没隔离 |
| Memory | `core/memory.py:MemoryManager`、`tools/memory_tool.py` | 文件型 CRUD，tool 模式；无 backend 抽象、无自动整理 |
| 子 Agent | `tools/delegate_tool.py:delegate_task` | 最成熟的子系统，有 task_id/status/token_usage，但缺 `stop_reason` 枚举、`step_events` 内嵌、loop detection |
| 工具系统 | `tools/registry.py:ToolRegistry` | 有热重载 + 子进程隔离；但每轮把**全部**工具 schema 都塞给模型，无延迟暴露 |
| 沙箱 | `core/sandbox_cleanup.py`、`sandbox/` | 只是共享磁盘目录 + 定时清理，没有虚拟路径隔离 |
| Skills | `core/skills.py`、`tools/skills_tool.py` | 目录扫描 + prompt 引导，无 metadata 发现/延迟加载/allowed-tools |
| 运行事件 | `core/agent.py:66` `_emit_event`（GUI 实时）；`autoresearch/observability/`（仅 AutoResearch 持久化） | 主循环事件**不落盘**，没有统一 append-only 事件流 |
| 安全 guardrail | `tool_call_guard` 回调（按调用方可选） | 非全局常开；无 read-before-write |
| 反思 | `tools/self_evolution_tool.py` | 轮后启发式建议，默认 dry_run |

## 剩余事项优先级（2026-08-11 重新排序）

前一阶段已经把 8 章主体铺开。现在不再按章节号推进，而按下面三个维度排序：

1. **收益**：能否明显改善真实使用中的正确性、上下文占用、安全或可调试性。
2. **风险**：是否会改写模型输入、自动写长期数据、改变文件路径等核心行为。
3. **可行性**：是否已有 ThreadState / middleware / event stream 等前置地基，可以小步落地并测试。

## 全局原则（贯穿所有章节）

摘自 deer-flow 学习文档第 16 章，作为每次改动的"验收心法"：

> 成熟 Agent 框架的关键不是让模型更会想，而是让**上下文、工具、记忆、委派、状态和观测**
> 都变成**可组合、可限制、可回放**的运行时机制。

具体到每次 PR / 改动，尽量满足：

- **不破坏现有能力**：R-Agent 目前能跑的 CLI (`main.py`) 和 GUI (`app_gui`) 不能因为升级而挂掉。
- **零配置可用性优先**：能不强制加 API key / 配置就别加（这是本项目一贯偏好）。
- **每处改动可回滚**：小步提交，配套测试示例。
- **先加旁路，再切主路**：新机制先以"可关闭开关"的形式加入，验证稳定后再默认开启。
