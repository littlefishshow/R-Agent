# 06 · 工具系统与沙箱

> 本章解释一个 Python 函数怎样变成模型可调用工具、工具为什么要延迟暴露和隔离执行、
> 大结果怎样落盘，以及 session sandbox 能隔离什么、不能隔离什么。实现快照：2026-08-14。

## 1. 工具调用不是“让模型直接执行 Python”

完整链路是：

```mermaid
flowchart LR
    P[工具模块 import] --> R[registry.register]
    R --> S[JSON Schema]
    S --> F[allowed/excluded/skill/deferred 过滤]
    F --> L[LLM 看到工具]
    L --> C[返回 tool_call 名称和 JSON 参数]
    C --> G[guard + 执行期权限检查]
    G --> X[隔离子进程执行 handler]
    X --> B[单结果与整轮预算]
    B --> M[tool message 写回]
```

模型只生成一个调用提案。真正执行仍由 `ToolRegistry`、权限检查和工具 handler 决定。

核心代码：

- `tools/registry.py:ToolRegistry`
- `core/agent.py:RAgent._loop`
- `tools/tool_search_tool.py`
- `core/context/budget_config.py`
- `core/context/tool_result_storage.py`
- `core/sandbox_workspace.py:SandboxWorkspace`
- `tools/file_tools.py`
- `tools/sys_tools.py`

## 2. 注册、热加载和 Schema

一个工具通过 `registry.register()` 注册四部分：

```python
registry.register(
    name="weather_lookup",
    description="查询一个城市的天气",
    parameters={
        "type": "object",
        "properties": {
            "city": {"type": "string"}
        },
        "required": ["city"],
    },
    handler=weather_lookup,
    metadata={"summary": "查询城市天气", "category": "web"},
)
```

注册表同时保存：

- 给模型看的 function schema；
- 程序真正执行的 handler；
- 用于工具目录的 summary/category metadata。

`get_all_schemas()` 会根据 `tools/*.py` 的修改时间和大小计算 signature；文件变化时重新
加载工具模块。因此新增工具通常不需要手改中央列表。

## 3. 四层工具权限

本轮工具集合按顺序收窄：

```text
注册表全量工具
  ∩ 外部 allowed_tools（若提供）
  ∩ active Skill allowed_tools（若激活）
  - exclude_tools
  → DeferredToolFilterMiddleware 只保留 always-on + promoted
```

随后执行每个 tool call 时还会再次检查：

1. 调用方 `tool_call_guard`；
2. Middleware `before_tool`；
3. `effective_allowed`；
4. `excluded`；
5. 工具自己的参数和审批规则。

这叫“schema 可见性 + 执行期”双重约束。即使恶意或异常模型猜到一个隐藏工具名，也不能
绕过执行期检查。

## 4. 延迟工具暴露

工具数量很多时，完整 schema 会占用大量 prompt token。开启
`DEFERRED_TOOLS_ENABLED=1` 后：

1. 常用工具和 `tool_search` 保持可见；
2. 其它工具只以 `name + summary + category` 出现在精简目录；
3. 模型先调用 `tool_search("auto research")`；
4. 匹配结果写入本次 run 的 `_promoted_tools`；
5. 下一轮对应完整 schema 才出现。

工具目录是请求级派生上下文，不写入 `self.messages`，不会逐轮累积。`_promoted_tools`
在每次新 `run_conversation` 开始时清空，不会永久扩大工具集。

运行时位置在 `DeferredToolFilterMiddleware.before_model()`。它位于
`ContextCompressionMiddleware` 前面，因此上下文 token 估算使用的是过滤后的真实工具
schema，而不是注册表全量 schema。

### 例子

```text
第 1 轮可见：read_file, write_file, tool_search, ...
模型：tool_search(query="分析 artifact 内容")
返回：artifact_inspect, artifact_search, artifact_slice
第 2 轮：这三个工具的完整 schema 被加入
```

代码默认关闭延迟暴露；当前本机 `.env` 已启用。

## 5. 工具进程隔离

普通工具通过 `execute_tool_isolated()` 在子进程执行。父进程：

- 用 Pipe 接收 JSON 字符串；
- 轮询 `cancel_event`；
- 到达 timeout 时 terminate/kill；
- 子进程异常时返回 JSON error，而不是让主循环崩溃。

### 平台差异

- macOS / Windows：使用 `spawn`，避免多线程进程 `fork` 的死锁和警告；
- Linux：保留 `fork` 以降低开销；
- 注册表快照通过 `cloudpickle` 传入，动态 lambda/closure 工具也可在 spawn 子进程使用；
- 快照无法序列化时，子进程退回重新加载模块定义工具。

`delegate_task` 是例外：它内部还会创建线程池、子 Agent、工具子进程和 Rich 看板，因此
父循环不再把它套进普通隔离子进程，避免嵌套进程和终端状态问题。

## 6. 中断、超时和返回协议

工具 handler 的正常结果会被包成：

```json
{"success": true, "result": "..."}
```

非法 JSON 参数、找不到工具、handler 异常、进程退出和超时都返回 `{"error": ...}`。
这使错误仍能作为 tool message 交给模型，让模型调整方案。

用户中断时父进程终止工具子进程，并抛出 `AgentInterrupted`，由对话外壳回滚半轮消息。

## 7. 大工具结果预算

上下文不能承受无限工具输出。R-Agent 使用三层策略：

1. 工具自身分页或限制数量；
2. 单个结果超过阈值时落盘；
3. 同一轮多个结果总量超预算时，优先把最大的结果落盘。

代码默认：

| 配置 | 默认值 |
| --- | --- |
| `R_AGENT_TOOL_RESULT_MAX_CHARS` | 80,000 字符 |
| `R_AGENT_TOOL_TURN_BUDGET_CHARS` | 160,000 字符 |
| `R_AGENT_TOOL_PREVIEW_CHARS` | 2,000 字符 |

落盘后模型收到：

```text
<persisted-output>
Path: sandbox/tool_outputs/...
Summary: ...
Preview: ...
</persisted-output>
```

完整正文不再塞入 prompt；`artifact_inspect/search/slice` 可按需回读。`read_file` 和
artifact 工具被设为无限单结果阈值，因为它们本身已经分页，避免“读 artifact 的结果又
被写成新 artifact”的循环。

`ThreadState.artifact_index` 还会记录路径、工具和 call id。

这部分当前由 `ToolOutputBudgetMiddleware` 和 `ToolResultTrackingMiddleware` 完成：

- `after_tool_execution`：单个超大结果外置；
- `after_tool_batch`：同一轮多个结果的聚合预算；
- `before_tool_message`：记录最终预算化结果，并更新 artifact/delegation 索引。

## 8. 工具结果安全

工具结果来自网页、文件或外部服务，不能天然信任。当前防线包括：

- 工具结果以 `role=tool` 进入消息，而不是 system；
- `ToolResultSanitizationMiddleware` 可 audit/enforce 注入短语；
- 已持久化占位块不重复清洗正文；
- 外部文件操作和危险命令由工具自身返回 `permission_required`；
- 删除工具要求明确 `confirm=true`；
- 运行命令有独立风险分析与短期审批记录。

安全不是一个正则就能完成，而是权限层级、执行 guard、参数审批和输出清洗的组合。

## 9. Session Sandbox

`SandboxWorkspace` 是默认关闭、按需创建的 session 目录：

```text
sandbox/sessions/<safe-session-id>/
├── workspace/
├── uploads/
├── outputs/
├── todo_lists/
├── run_events/
├── tool_outputs/
└── delegate_contexts/
```

虚拟路径映射：

| 虚拟路径 | 本地位置 |
| --- | --- |
| `/mnt/user-data/workspace` | session `workspace/` |
| `/mnt/user-data/uploads` | session `uploads/` |
| `/mnt/user-data/outputs` | session `outputs/` |
| `/mnt/skills` | 仓库 `skills/`（只做路径映射） |

### 文件工具路由

开启 `SESSION_SANDBOX_ENABLED=1` 且 session 非空时：

- 相对路径以 session `workspace/` 为根；
- `/mnt/...` 走虚拟路径映射；
- 路径穿越被拒绝；
- host 绝对路径仍是绝对路径，并进入工作区外审批逻辑。

### 当前按 session 路由的子系统

- file tools 的相对路径；
- Todo 文件；
- Run events；
- 大工具输出；
- delegate context artifacts。

tool outputs 和 delegate contexts 目前通过环境变量把路径传进隔离子进程：
`R_AGENT_TOOL_OUTPUTS_DIR`、`R_AGENT_DELEGATE_CONTEXTS_DIR`。沙箱关闭时 Agent 会清除，
避免上一次 session 污染下一次运行。

## 10. Sandbox 不是什么

这层是路径路由和会话隔离兼容层，不是强安全容器：

- 工具进程仍运行在同一台主机；
- 允许审批后访问 host 绝对路径；
- `/mnt/skills` 映射到共享仓库 Skills；
- 环境变量是进程级状态，并发多个配置不同的 Agent 时需要谨慎；
- 没有 Linux namespace、seccomp、容器镜像或网络隔离。

因此应称为 **session workspace isolation**，不能宣传成完整恶意代码沙箱。

## 11. 文件工具审批例子

在 session sandbox 中写相对路径：

```json
{"path": "report.md", "content": "..."}
```

实际写入 `<session-root>/workspace/report.md`，无需工作区外授权。

读取 `/Users/example/secret.txt` 时，第一次返回：

```json
{
  "permission_required": true,
  "risk_level": "medium",
  "absolute_path": "/Users/example/secret.txt"
}
```

工具不会在隐藏子进程里 `input()` 等待。Agent 必须先向用户解释，只有明确同意后才能用
`allow_outside_workspace=true` 重试。

## 12. 当前边界

- deferred promotion 只在当前 run 有效；
- catalog 是词法匹配，不是语义路由；
- 工具热加载失败会打印 warning，单个模块失败不阻止其它工具；
- spawn 依赖 `cloudpickle`，requirements 已声明；
- session sandbox 默认关闭；
- `R_AGENT_TOOL_OUTPUTS_DIR` 等全局 env 对多 Agent 并发不是最理想的显式上下文传递；
- ToolRegistry 子进程是故障隔离，不等同于权限隔离；
- 文件工具仍允许用户明确授权后访问工作区外路径。

## 2. deer-flow 是怎么做的

- **工具来源聚合** `tools/tools.py:get_available_tools()`：config + builtins + MCP + ACP + memory/subagent tools；去重、按 tool group 过滤、按模型能力决定 vision tool、按沙箱策略隐藏 host bash。
- **9.2 deferred tools / MCP routing**：不全量绑定 MCP schema；建 deferred catalog；prompt 只列工具目录；`tool_search`/MCP routing middleware 按需提升；`DeferredToolFilterMiddleware` 隐藏未提升工具。
- **9.3 沙箱生命周期** `sandbox/middleware.py`：lazy init（首次工具调用才创建）；sandbox id 写入 state 而非局部变量；lazy 初始化后用 `Command(update={"sandbox": ...})` 合并进状态；子 Agent 继承父 sandbox/thread_data；shutdown 时 provider 清理。
- **虚拟路径约定**：`/mnt/user-data/workspace`（临时）、`/mnt/user-data/uploads`（上传）、`/mnt/user-data/outputs`（产物）、`/mnt/skills`（技能）。

**9.3 原文：** 工具层必须知道自己在哪个隔离环境里，sandbox id 必须是可 checkpoint 的状态。

## 3. R-Agent 打算怎么改（简略步骤）

分两条线，都偏工程化增强，可独立推进。

### A. 工具延迟暴露（收益：上下文瘦身 + 选工具更准）
1. **建工具目录**：给每个工具的 `register` 增加轻量 metadata（一句话摘要 + 分类），`get_tool_catalog()` 只返回"名字 + 摘要"。
2. **prompt 只给目录**：默认在系统上下文里列工具目录，而非全量 schema。
3. **加 `tool_search` 工具**：模型按需检索并"提升"某工具，之后该工具的完整 schema 才对模型可见（配合 `01` 的 middleware 做 `DeferredToolFilter`）。
4. **加开关**：小工具集（如 R-Agent 默认）可关掉延迟暴露、退回全量（零配置友好）；工具很多或接 MCP 时开启。

### B. 沙箱虚拟路径与生命周期（收益：隔离、可 checkpoint）
5. **per-session 工作区**：把 `sandbox/` 下的散目录整理为 per-session 根，映射虚拟路径 `workspace/uploads/outputs`（对齐 deer-flow 约定，但用相对/本地路径，不强套 `/mnt`）。
6. **sandbox id 进 state**（依赖 `02`）：`ThreadState.sandbox` 保存当前工作区 id，子 agent 继承父工作区（与 `05` 协同）。
7. **lazy init**：首次文件/命令类工具调用时才创建工作区，无 IO 任务不建目录。
8. **沿用现有清理**：`sandbox_cleanup` 逻辑保留，只是清理单位从"全局散目录"变成"per-session 根"。

> 关键约束：R-Agent 默认工具不多，延迟暴露**默认可关**，保证零配置行为不变；沙箱改造以"不破坏现有 `sandbox/` 使用方"为前提，先并存后迁移。

## 4. 为什么这样改

- **为什么延迟暴露对小工具集默认关**：R-Agent 默认约 30 个工具，全量 schema 尚不至于撑爆上下文；默认全量最省事、零行为变化。延迟暴露真正的价值在"工具很多或接入大量 MCP 工具"时——那时一个开关即可开启，用目录 + `tool_search` 把上下文占用降下来。
- **为什么提升逻辑放在主循环而不是工具内部**：R-Agent 的工具跑在 `execute_tool_isolated` 的**fork 子进程**里，子进程改不了父进程的 `_promoted_tools`。所以 `tool_search` 只做纯检索、把结果通过管道返回，主循环解析结果再提升——这是被 R-Agent 现有隔离架构决定的、唯一正确的接法。
- **为什么 always-on 里放 tool_search/todo_manage/delegate_task 等**：延迟暴露不能把"检索工具的工具"也藏起来（否则模型没法自救）；调度类（todo/delegate）和交互类（present_files/ask_clarification）是任何任务都可能立即要用的骨架能力，常驻可见更稳。
- **为什么虚拟路径不强套 `/mnt`**：deer-flow 跑在容器里，`/mnt/user-data/...` 是容器约定；R-Agent 是本地进程，强套绝对路径反而别扭。真要做 B 线，用相对/本地 per-session 根即可，保留同样的 workspace/uploads/outputs 语义。
- **为什么 Todo/file tools 要隔离，但 GUI 资料库不能跟着隔离**：Todo、运行事件和 Agent 临时文件属于某次执行，适合按 session 隔离；Cockpit 的 `outputs/` 则是用户长期维护的共享资料库，里面有 papers 与阅读笔记，切换 chat session 后仍应可见。两者职责不同，不能为了目录形式统一而让 GUI 丢失已有资料。
