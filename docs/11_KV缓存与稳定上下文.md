# 11 · KV 缓存与稳定上下文

本章描述当前 R-Agent 为 KV cache 稳定性增加的三项能力：本地前缀复用率、Durable
current/next 双版本，以及不改写顶层 `tools=` 的动态工具调用。

## 1. Harness 主指标：本地 KV 复用率

R-Agent 使用本地请求结构评估 harness 是否保持了可复用前缀，不再用 provider 的实际
缓存保留结果给 harness 打分：

```text
local_reuse_ratio = local_reusable_tokens / local_prompt_tokens
session_local_reuse_ratio = Σlocal_reusable_tokens / Σlocal_prompt_tokens
```

`local_prompt_tokens` 使用与上下文压缩相同的本地 token 估算器，包含 messages 和 tools。
`local_reusable_tokens` 的计算规则是：system/catalog/durable/tools 必须相同，然后计算新旧
conversation 的最长公共完整 message 前缀；固定组件和公共消息前缀的估算 tokens 都视为可复用。
任一固定组件变化时，本轮从 0 开始。第一轮是冷启动，复用率为 0。

会话值按 token 加权，不能把每轮百分比做算术平均。这个指标回答的是“如果 provider 正常
支持前缀缓存，harness 理论上能复用多少”，不受路由分片、TTL、驱逐和 provider 上报影响。

本地同时计算请求组件哈希：

- system；
- tool catalog；
- durable current；
- 顶层 tool schemas；
- 组合 prefix。

同时输出 `tail_append_only`、
`tool_schema_changed`、`durable_changed`、`history_rewritten`、
`context_compacted` 等原因，解释复用率为什么变化。

CLI 在 token 状态后显示本轮/会话本地复用率和前缀原因；Cockpit 输入框上方显示可复用
估算 tokens、前缀变化与请求耗时。GUI session state 也暴露完整 `cache_usage`。

Provider 的 `cached_tokens` 仍记录在 `provider_*` 字段中，只用于端点诊断，不参与主百分比。

## 2. Durable current / next

```text
durable_current  --模型每轮读取，压缩之间逐字节冻结
durable_next     --运行中积累，不进入当前请求前缀
```

`next` 收集：

- 滚动 summary；
- pending/in_progress/needs_split/blocked/failed Todo；
- 已发现动态工具的完整契约与 schema hash；
- skill_context 与 active_skill_policy；
- delegation ledger；
- artifact index；
- hidden-user memory snapshot。

压缩或手动归档成功后执行一次原子晋升：

```text
stage live channels -> render next -> next becomes current -> epoch += 1
```

GUI 持久化 current/next 及相关结构化 channel。恢复时复用 current 已保存的 content，不从
live state 临时重渲染，因此不会在无压缩的情况下意外改变前缀。

### 2.1 父子委派的批次公共前缀

`delegate_task` 在启动并发子 Agent 前只读取一次 Todo/Memory，构造批次级
`delegation_prefix_snapshot`。所有兄弟子 Agent 共用完全相同的静态 System Prompt、Durable
Current、Catalog 和固定 Tool Schema；task id、goal、依赖和验收标准只放在尾部 User Message。

子 Agent claim/update Todo 后，新状态通过尾部 tool result 立即可见，并进入该子 Agent 的
durable next，不修改批次公共 current。父 Agent只收到紧凑 delegate result，仍保持尾部追加。

子 Agent 的 `local_prompt_tokens/local_reusable_tokens` 通过 `delegated_cache_usage` 汇总给父
Agent。CLI/Cockpit 展示 parent、children 和 overall 三个 token 加权复用率。每个子 RAgent 的
第一轮仍保守计为冷启动；同批跨子 Agent 的共享条件另外由一致的 `delegation_prefix_hash`
验证。

## 3. 稳定动态工具

Deferred tools 开启时，顶层 `tools=` 只含固定常驻工具和两个控制工具：

```text
tool_search
invoke_dynamic_tool
```

`tool_search` 把匹配工具的 `name/description/parameters` 完整契约写进自己的 tool result。
这是对话尾部追加，不改写已缓存前缀。模型随后调用：

```json
{
  "name": "invoke_dynamic_tool",
  "arguments": {
    "tool_name": "目标工具",
    "arguments": {}
  }
}
```

父 Agent 不信任消息内容，会再次检查：

1. 工具已经被当前会话发现；
2. 工具仍存在于真实 Registry；
3. Registry schema hash 与发现时一致；
4. allowed/excluded 和 active Skill policy 允许；
5. 常用 JSON Schema 参数类型与 required 字段通过；
6. `tool_call_guard` 允许；
7. 最终仍在隔离工具进程中执行。

这样牺牲了动态工具的原生 per-function 顶层 schema，换来稳定的固定工具前缀；基础常用工具
仍保留原生 Function Calling。

## 4. 可比指标

评估改造效果时至少比较：

```text
local_prompt_tokens
local_reusable_tokens
local_new_tokens
kv_reuse_ratio
last_local_prompt_tokens
last_local_reusable_tokens
last_kv_reuse_ratio
last_request_latency_ms
last_prefix_change_reasons
component_hashes
```

应分别统计主 Agent、子 Agent 和内部摘要调用；当前 `cache_usage` 聚焦有 request fingerprint
的主 Agent 请求，避免内部摘要请求污染交互复用率。`provider_cached_prompt_tokens` 和
`provider_cache_hit_ratio` 作为次级诊断保留，但不评价 harness 好坏，也不能代表理论复用能力。

## 5. 2026-10-17 AIDP 实测结论

使用 `scripts/diagnose_prompt_cache.py` 对当前配置的 `gpt-5.5-2026-04-24` 端点做了受控
实验。输出严格限制为极短文本，结果保存在 `outputs/cache_diagnostics/`。

| 场景 | 结果 |
| --- | --- |
| 固定短文本、同 client、完全相同请求 | 0/4 命中 |
| 固定 tools、完全相同请求 | 0/4 命中 |
| 固定 tools、对话只在尾部追加 | 冷启动后 3/3 命中，单轮约 88%～90% |
| 同一前缀从 shared client 切到 fresh client | 冷启动后 3/3 命中，均约 78.6% |
| 真实 R-Agent 形状（约 8K prompt tokens） | 冷启动后 3/3 命中，均约 96% |
| R-Agent 前缀 + 约 58K prompt tokens 长尾 | 后两轮约 99.8%，缓存 57,984 tokens |
| R-Agent tool-call/tool-result 历史 | 前三轮命中 46%/76%/80%，第 4 轮无本地前缀变化却归零 |

由此排除：tools/function calling 完全不支持缓存、长上下文完全不缓存、client 或
`X-TT-LOGID` 是缓存必要边界。端点能够正确缓存 R-Agent 形状、长上下文和 tool 历史，
但不同 prefix hash 的表现差异很大，同一尾部追加链也可能从命中突然降到 0。

当前最符合证据的解释是 provider 侧 best-effort cache、路由分片或驱逐策略不稳定。
本地 `tail_append_only` 仍是必要条件，但不能保证服务端命中。若要进一步定位到具体实例，
需要 provider 暴露 backend/replica id、cache shard 或有效 request id；当前兼容端点的
SDK response `_request_id` 为 `null`。
