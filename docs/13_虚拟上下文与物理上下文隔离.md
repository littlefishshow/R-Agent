# 13 · 虚拟上下文与物理上下文隔离

> 本章解释 R-Agent 如何把"会话一路发生了什么"（虚拟上下文时间流）与"模型这一轮看得见
> 什么"（物理上下文窗口）隔离开，让上下文压缩不再丢失历史，支撑排查 bug 与 Agent 溯源。
> 实现快照：2026-10-19。依赖：`03_上下文管理`、`08_运行事件流`、`12_L0_Provider与流事件层`。

## 1. 要解决什么问题

原本 R-Agent 只有一个**物理上下文** `ThreadState.messages`：它既是真相，又是发给模型的
窗口。上下文压缩（`_maybe_compress_context` / `_compress_after_archive`）会**就地**把旧消息
替换成一条摘要——原始完整消息随之从内存消失。这让排查 bug 和"Agent 回忆过去任务"失去
可靠底座：

- `RunEventStore`（`08` 章）是 per-run、只存预览、fail-open 丢事件，不能重建历史；
- GUI `ContextSnapshotStore` 的 fork/truncate 也是破坏性重写，且只服务 GUI。

## 2. 设计：虚拟 vs 物理（两者隔离）

```text
真相源（虚拟上下文）                     投影视图（物理上下文）
core/context_log.py:ContextLog   ──记录──>   ThreadState.messages（发给模型的有界窗口）
 append-only / 无损 / 会话级 / 落盘            可被压缩/重建/KV 稳定化，丢了也能复原
```

两条不变量：

1. **ContextLog 只增不改不删**。压缩不删数据，只追加一个 `fold` 标记（记录被折叠的
   `[start_seq, end_seq]` 区间与摘要）；原始消息仍以其 entry 留在日志里。
2. 物理上下文始终可从日志复算，因此它可以安全地被压缩。

## 3. 与 L0 事件流的衔接

这是把 `12` 章的 L0 和本章接起来的关键：

- **L0（`core/llm`）是模型侧事件源**：`AssistantMessageEvent` 描述一次响应如何产生，
  `AssistantMessage` 是其最终归约；
- **ContextLog 是会话侧事件源**：把每条进入对话的消息、每次折叠、每次 durable 晋升、
  每轮 run 边界，按 `seq` 追加成一条可回放的时间流。

衔接点在 `core/agent.py`：主循环拿到 L0 最终消息后，既把可序列化 dict 追加进物理
`messages`，又调用 `_log_context_message(message, thinking=_thinking_of(message))` 把它无损
镜像进虚拟上下文。注意 **thinking**：物理 `messages` 丢弃模型思考内容，但 L0 最终消息里的
`reasoning_content` 被虚拟上下文完整保留，便于溯源"模型当时怎么想的"。

一句话：L0 回答"这一次模型调用怎么产生的"，ContextLog 回答"这个会话一路发生了什么、
为什么模型现在看不到早期内容"。

## 4. 记录了哪些 entry

| type | 时机 | 内容 |
| --- | --- | --- |
| `user` / `assistant` / `tool_result` / `system` | 消息进入物理历史时 | 无损原文（assistant 附带 thinking） |
| `fold` | 自动压缩 / archive_subtask 成功 | 被折叠区间 `[start_seq, end_seq]` + 摘要 + 统计 |
| `durable_promote` | durable next → current 晋升 | 新 epoch 的 durable 内容与 hash |
| `run_start` / `run_end` | 每轮用户对话首尾 | run_id、模型、是否截断 |

`seq` 在会话内单调递增、**跨 run 连续**，用于确定性排序与折叠区间引用。

## 5. 压缩如何映射成 fold（无损）

压缩器保留开头第一条 system 消息，并把最早的若干**对话**消息折叠成摘要。
`_log_context_fold` 据 `stats.summarized_messages` 条数，在已镜像的消息里跳过那条常驻
leading system，取最早、尚未折叠的 N 条，记录它们的 `[start_seq, end_seq]` 并追加 fold
标记。原始消息仍留在时间流里：

```text
物理 messages：  [system] [摘要] [最近N条]        ← 早期原文已被替换
虚拟 ContextLog：#1 system  #2 user(原文)  #3 assistant(原文)  …  #k fold(折叠 #2..#3)
                                   └─ slice(2,3) 可无损取回 ─┘
```

即便计数与物理层略有出入，日志仍是无损的——fold 边界只用于回放便利。

## 6. 溯源能力

### 6.1 给人：回放脚本

```bash
python3 scripts/replay_context.py --list              # 列出所有会话时间流
python3 scripts/replay_context.py <session>           # 按 seq 回放时间线
python3 scripts/replay_context.py <session> --expand  # 展开 fold 段的原始消息
python3 scripts/replay_context.py <session> --json    # 原样打印每条 entry
```

### 6.2 给 Agent：溯源工具（`tools/context_recall_tool.py`）

- `context_search(query)`：在整条时间流（含已折叠段）里按关键词定位某句话/文件/结论
  最早出现在哪条消息，返回 seq 与所在折叠区间；
- `context_recall(start_seq, end_seq)`：取回被折叠掉的原始消息原文。

工具进程直接读会话落盘的 `<session>.context.jsonl`，与写入端解耦，可作为延迟工具按需
发现调用，天然不占稳定前缀 token（见 `06` / `11` / `12`）。

## 7. 落盘与隔离

每个会话一个 `<dir>/<session>.context.jsonl`，默认 `sandbox/context_log/`；启用 per-session
沙箱时迁入 `<session-root>/context_log/`（与 run_events 一致）。写入 fail-open（不拖垮
主循环），但内存 entries 始终完整，`slice` / `search` 据此做无损回放。

## 8. 配置开关

| 配置 | 默认值 | 作用 |
| --- | --- | --- |
| `CONTEXT_LOG_ENABLED` | `1` | 是否维护虚拟上下文时间流；`0` 完全回退到仅物理上下文 |
| `CONTEXT_LOG_DIR` | `sandbox/context_log` | 时间流落盘目录 |

关闭时不创建时间流、不落盘，行为与接入本章前完全一致。

## 10. 当前边界

- fold 的 seq 映射是 best-effort（跳过 leading system 后按 `summarized_messages` 取数）；
  日志本身始终无损，映射只影响回放时的区间展示；
- 虚拟上下文记录的是"进入过物理历史的消息"，不包含每轮临时投影的 durable/catalog
  （它们由 `durable_promote` 元事件单独追踪）；
- 目前 GUI 的 fork/truncate 仍走 `ContextSnapshotStore` 的消息重写，尚未改为在时间流上
  追加 `branch` 锚点（已预留 `ET_BRANCH` 类型，属于后续工作）；
- 物理窗口尚未改成"纯从 ContextLog 投影"——当前是"物理 messages 为主、虚拟上下文旁路
  镜像"，先保证低风险与可回退；把 `messages` 变成纯投影是更彻底但触点更多的下一步。
